```bash

python "$B" --list-presets
```

## 2. Нюансы (то, что реально вылезло — уже учтено в скилле)

1. **ffmpeg здесь — Windows-бинарь** (`/c/ffmpeg/bin`). Аргументы в стиле MSYS
   (`/c/Users/...`) он не понимает: `Error opening output ... No such file or
   directory`. Пути для ffmpeg — только `C:/Users/...`. Сам bash (`ls`, `cd`)
   MSYS-пути принимает.
2. **Один тестовый отрезок врёт.** На одном файле при *одинаковых* настройках
   битрейт отрезков отличался в 1,6× (75,8 против 122,4 кбит/с). Тестировать
   минимум два отрезка и брать худший.
3. **Источник уже сжат — оценки занижаются.** Фильм пришёл с 1107 кбит/с, и x265
   охотно тратил битрейт на сохранение зерна исходного кодера. Первый прогноз
   «540p CRF 28 ≈ 45–55 МБ» дал **88 МБ (2,8×)**. К интуитивному CRF добавлять
   +4…+6.
4. **Аудио — это не бесплатно.** AAC 48k моно × 1482 с = 8,9 МБ, т.е. 28 % от
   цели в 32 МБ. Считать аудио в бюджете всегда.
5. **CRF-лестница:** +6 CRF ≈ вдвое меньший битрейт (здесь ≈1,15× на +1 CRF).
   Это главный рычаг точной подгонки.
6. **10× на 720p без уменьшения разрешения физически нет.** 137 кбит/с на всё —
   это 640×360 / 15 fps. Обещать «720p в 10 раз» нельзя.
7. **Мелочи, которые надо не забывать:** `-movflags +faststart` (мгновенный старт
   и перемотка), `-tag:v hvc1` (Apple/QuickTime), **оригинал не трогаем** — новый
   файл с суффиксом кратности, `-crf` и `-b:v` вместе не использовать (CRF молча
   игнорируется).
8. **Совместимость:** H.264 + AAC в MP4 играет везде. HEVC — в VLC и почти везде,
   но не во встроенном плеере Windows без HEVC-расширения. **Opus внутри MP4 —
   нестандарт** (VLC играет, остальные могут нет). AV1 — VLC 3.x играет, но вне
   этого ПК декодера обычно нет.
9. **Денойз не помог:** `hqdn3d` изменил битрейт меньше чем на 1 % (121,26 против
   122,42 кбит/с) — источник уже очищен. Не тратить на это время, пока источник
   не шумит visibly.
10. **NVENC не нужен.** `libx265 -preset medium` дал 255–350 fps на 360–540p:
    25-минутный фильм кодируется за 1–2 минуты. NVENC — только если надо за секунды.
11. **Кураторы/авто-скиллы.** Скилл `video-compression` создан куратором
    автоматически из этой сессии (14:31), скрипт был непроверенным — я прогнал его
    на реальном файле. Перед массовыми правками скиллов ставить
    `hermes curator pause`, иначе куратор может переписать/консолидировать.

## 3. Предложения — что доработать (по приоритету)

### P1. Батч по папке ✅ сделано, осталось:
- `--jobs N` — параллельная обработка (сейчас последовательно; при 25-мин файлах
  и 1–2 мин на энкод это не критично, но на 50+ файлах станет узким местом).
- **Манифест с resume по схеме `video-batch-runner`** (JSON-lines, `pending/running/done/failed`,
  уникальный `id`). Сейчас идемпотентность есть («готовый файл пропускается»), но
  состояния `failed` между запусками не сохраняются.

### P2. Авто-подбор CRF ✅ сделано (`--target`), улучшение:
Сейчас перебор идёт шагом CRF ±2 и целится в **худший** отрезок, из-за чего
результат уходит в меньшую сторону (цель 5× → факт 5,75×). Доработка: шаг +1 на
финальной итерации и целеуказание по средней двух отрезков, когда условие
«не меньше N×» — тогда попадание будет в пределах ±5 %.

### P3. Файл пресетов вне кода
`presets.json` рядом со скиллом вместо словаря в скрипте — чтобы менять профили
(например, добавить «для телефона» 540p/24/CRF30) без правки Python.

### P4. Точный размер вместо «примерно»
2-фазный ABR (`-b:v <бюджет> -pass 1/2`) даёт ровно заданный размер; CRF даёт
лучшее качество при том же среднем. Доработка: флаг `--exact-size 25MB`, который
считает бюджет и запускает 2-pass. На этом файле не тестировалось.

### P5. Пред-проверка источника
Если `vbitrate ≤ 1500 кбит/с` — печатать предупреждение «источник уже сжат,
10× здесь даст заметную потерю; рассмотрите 5×» и печатать оба варианта. Этот
файл — ровно такой случай (1107 кбит/с).

### P6. Объективная оценка потери качества
Считать VMAF/SSIM между оригиналом и результатом вместо «мягко/смотрибельно».
Сначала проверить, есть ли `libvmaf` в текущей сборке ffmpeg (`-filters | grep vmaf`).
Полезно для выбора между A и B на конкретном файле.

### P7. 10-бит x265 (`-pix_fmt yuv420p10le`)
На низком битрейте обычно даёт лучше картинку при том же размере, но совместимость
хуже (старые ТВ/телефоны). Протестировать на одном файле и сравнить.

### P8. Метаданные и субтитры
Сейчас не переносятся. Добавить `-map_metadata 0` и `-c:s copy` (если в исходнике
есть дорожки субтитров) или явно удалять (`-map 0:v:0 -map 0:a:0`).

### P9. Многоканальный звук
Downmix 5.1 → стерео (`-ac 2`) на исходниках с 6 каналами — сейчас логика только
моно/как-есть.

### P10. Проверка воспроизведения
Автопроверка сейчас: ffprobe-метаданные + полный проход декодирования
(`ffmpeg -v error -i out -f null -`) — ловит битый битстрим. Чего нет: реального
открытия в VLC/TV/телефоне. Оставлено на ручную проверку.

### P11. Хранение отчёта
`--report out.json` уже есть; сделать его форматом манифеста с resume (см. P1) и
дописывать `crf`, `factor`, `seconds` для каждого файла — чтобы через полгода
знать, какими настройками сделан каждый `_x10`-файл.

### P12. Дисциплина пресетов
Держать A и B зафиксированными: одна кратность = одни настройки для всех файлов.
Иначе «сжатые» файлы в папке станут несравнимыми.
