# Гиды «что мы узнали в проекте» для Юрия

Класс задачи: по завершённому этапу (пайплайн, разбор, переезд) написать **долговечные
справочные документы для самого Юрия** — не скилл, а объяснение с числами, которое он будет
перечитывать через месяцы, плюс конвертация в Word, если он просит. Формулировки-триггеры:
«хочу, чтобы то, что я пережил, я мог вспомнить», «запиши всю эту информацию», «сделай файл
для любознательного разработчика», «сделай выжимку по проекту», «переформатируй в Word».

Не путать: процедура («как делать») уходит в скилл, гид — объяснение («как это устроено и
почему так сделано») + измеренные числа. Скиллы и так синкаются между ПК
(`hermes-skills-cross-pc-sync`), гид же — ещё и читаемый человеком текст.

## When to Use

- Юрий просит записать/объяснить то, через что проект уже прошёл: «хочу, чтобы я мог
  вспомнить», «запиши всю эту информацию, которую я ощупал руками», «сделай файл для
  любознательного разработчика», «сделай выжимку по проекту».
- Закончён крупный этап, и есть измеренные числа (время, деньги, объёмы) — их надо сохранить
  с указанием источника, пока они ещё под рукой.
- Он просит перевести готовый .md в Word (или «переформатировать» его документ).

## Три вида документа — сначала определи, какой заказан

| | Гид «что мы узнали» | Инструкция для новичка «как пользоваться» | Список отложенных вопросов |
|---|---|---|---|
| Триггер | «чтобы я мог вспомнить», «выжимка по проекту» | «для любого, кто будет работать на этом ПК», «начинающий разработчик», «как конечный результат» | «все проблемы, которые я отложил на потом — подробный список» |
| Содержание | механика, числа, грабли, открытые задачи (структура §4) | **только текущее состояние**: что где лежит, ежедневные шаги, что делать при ошибке, чего нельзя | сводная таблица + карточка на каждый пункт (см. ниже) |
| Исключить | — | историю («раньше было…»), грабли, через которые прошли, нерешённые вопросы, «пока не сделано» | уже сделанное и пересказ сессий |

**Список отложенных вопросов.**
- Источники: текущий чат (каждый вопрос агента без ответа, «буду обдумывать», «не трогал»),
  связанные чаты по теме (`session_search` по названию), разборы других агентов,
  «на будущее»-разделы старых документов. **Каждый факт перепроверь на диске** (счётчики,
  есть ли файл, `git log -- <путь>`) — память о сессии стареет.
- Форма: вверху таблица «№ / вопрос / приоритет / кто закрывает», потом на каждый пункт:
  **Сейчас → Почему важно → Варианты → Рекомендация → Нужно от Юрия / как закрыть**.
  В начале файла правило: закрытый пункт удаляется, решение уходит в CHANGELOG.
- В ответе выдели пункты, закрываемые одним «да/нет», и те, что дешевле сделать **до** следующего
  шага (напр. переписать историю git до подключения других ПК).
- Клади рядом с инструкцией новичка, ссылку — в README, **но не в инструкцию**: там
  нерешённым вопросам не место. Имя — как у соседней инструкции (в репо скиллов —
  `ОТЛОЖЕННЫЕ-ВОПРОСЫ-СИНХРОНИЗАЦИИ.md`).

Для инструкции новичка: перед тем как писать — найди уже существующие документы по теме
и скажи, почему они не подходят (слишком краткие / содержат историю и грабли / написаны
для агента); перескажи своё понимание задачи + предложи имя, место и оглавление, дождись
«да». Клади в корень синхронизируемого репо (тогда файл есть на всех ПК) и ставь ссылку
первой строкой README. Каждую команду прогони на живом ПК, прежде чем вписать.
**Сначала приведи в порядок то, что описываешь** (незакоммиченные скиллы, скрипты
вне репо), потом пиши инструкцию: иначе «конечный результат» в тексте будет неправдой, а
наведение порядка заодно проверяет команды инструкции.

Не для этого скилла: правка процедуры для будущего агента (это обычный `skill_manage patch`
в том скилле, который описывает процедуру) и разовая выдача ответа в чат без файла.

## 1. Уровень читателя

Он просит «для подготовленного разработчика, но не для слишком профессионального специалиста».
Значит:

- сначала одна мысль/аналогия человеческим языком, потом механика и детали;
- **каждое сокращение — в глоссарий-таблицу в конце файла**, даже привычные (OCR, API, TTS).
  Ради этого глоссария файл и заказывают; самая частая претензия — «а что это значит?»;
- не «всё работает», а числа: минуты, знаки, доллары, RTF, размеры, проценты;
- таблицы вместо абзацев там, где сравниваются варианты — он читает таблицы.

## 2. Куда класть файлы

- **Рядом с материалом проекта** и уже существующей выжимкой (одна папка с исходниками), а не
  в scratch и не в home.
- **Имена файлов — ASCII** (`GUIDE-01-text-extraction-and-translation.md`): у него правило
  ASCII-имён, даже когда рядом лежат кириллические исходники. Текст внутри — русский.
- **Кодировку брать у соседей, а не из общего правила:** `head -c 3 <соседний>.md | xxd -p`;
  `efbbbf` — UTF-8 с BOM. У его собственных документов BOM норма, но в проектных репо .md
  лежат и без BOM — повторяй то, что в папке. `write_file` BOM не добавляет: дописывай
  `b"\xef\xbb\xbf"` в начало и проверяй первые 3 байта после записи.
- Один гид на один смысловой блок пайплайна (напр. «текст → перевод» и «текст → речь»), а не
  один гигантский: просил именно так — «давай сделаем два файла».

## 3. Факты: откуда брать (здесь теряется доверие)

- **Железо — с живой машины, никогда из профиля/памяти.**
  `nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv`;
  `powershell -NoProfile -Command "(Get-CimInstance Win32_Processor).Name; (Get-CimInstance Win32_ComputerSystem).TotalPhysicalMemory"`
  (`wmic` на этой Windows уже не отвечает). В одной сессии профиль обещал RTX 4060 / 32 ГБ, а
  на машине стояли RTX 3050 / 16 ГБ — все оценки времени рендера были бы выдумкой.
- **Числа проекта — из его же артефактов:** логи стадий, индексы разделов, файлы результатов,
  метаданные исходников (`creator`/`producer` PDF часто и есть корень проблемы). Считай
  скриптом (суммы, количество файлов, длительности), а не по памяти о сессии.
- **Помечай источник каждого числа:** `[замер]` (измерено здесь), `[бенч]` (внешнее измерение,
  укажи на каком железе), `[оценка]` (расчёт, назови множитель). Там, где не измеряли, писать
  «не измерено» — правдоподобное число хуже отсутствия.
- **Открытые/незавершённые пункты — отдельным разделом.** Он решает по ним, что брать дальше.
- **Найденные расхождения (железо, кодировки, версии, дубли) — сообщить отдельным блоком в
  ответе**, а не тихо исправить. Это половина ценности такой сессии.
- Пересчитывай чужие бенчмарки на его машину: цифры с RTX 3090 Ti умножаются на ~4–6 для 3050;
  без этого таблица скорости обманывает.

## 4. Структура, которая сработала

1. машина + как это проверено (команды);
2. главное в одном абзаце;
3. механика по слоям (термины → определения);
4. диагностика: числа и пороги («чистый слой 99 %+, битый 0–80 %»);
5. развилка таблицей «когда что выбирать»;
6. грабли: одна строка на граблю + механизм, почему так;
7. что улучшить дальше — по возрастанию цены/сложности («лестница»);
8. глоссарий сокращений;
9. чеклист нового проекта;
10. таблица «где что лежит» (пути к скриптам, окружениям, логам);
11. открытые задачи со ссылкой на постановку.

## 5. Отдача

- Каждый файл — отдельной строкой `MEDIA:<абсолютный путь>`; в ответе — короткий обзор: что
  внутри каждого, что нашлось при проверке, что не закрыто. Без пересказа всего текста.
- **Word по запросу.** Нужен pandoc (`where pandoc`; обычно `%LOCALAPPDATA%\Pandoc\pandoc.exe`):
  ```
  pandoc in.md -o out.docx -f gfm --toc --toc-depth=2 \
    --metadata title="Гид 1. ..." --metadata lang=ru-RU --columns=100
  ```
  Проверка результата (не на глаз): прочитать `word/document.xml` из .docx как zip и сверить
  число `<w:tbl>` с числом таблиц в .md — так ловится тихая потеря таблиц при конвертации.
  Имя .docx — ASCII, в ту же папку. Красивее (его оформление) — предложить `--reference-doc`
  с любым его .docx как шаблоном стилей.

## Грабли

- Не превращай гид в скилл и наоборот: скилл — процедура для будущего агента, гид — объяснение
  для человека. Дублирование текста между ними расходится через месяц.
- Не переписывай выжимку/постановку задачи, существующую в папке, — добавляй новый файл и
  ссылайся на неё.
- Длинный ответ о такой работе дроби и проверяй язык: у него раздражает мешанина языков, а
  длинные отчёты срываются в другой язык. Всё по-русски.
- После сессии правок скиллов/гайдов не забудь про commit+push репо (`hermes-skills-cross-pc-sync`)
  и скажи про незакоммиченное состояние, если оно есть, вместо тишины.
- Источники для такого гида обычно уже описаны в скиллах — например `book-translate-and-voice`
  (перевод + озвучка) и `pdf-broken-text-layer-repair` (битый слой PDF): оттуда берутся
  процедуры и пороги, но числа перепроверяются на живых артефактах.
