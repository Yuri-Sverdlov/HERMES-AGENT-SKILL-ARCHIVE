# Синхронизация скиллов Hermes между ПК через GitHub

Аудит копий по хешам; общий git-клон, подключённый к Hermes через
`skills.create_dir` + `skills.external_dirs`.

## When to Use

Аудит/наведение порядка в скиллах, перенос скилла на другой ПК, подключение
нового ПК к общему репо скиллов, сравнение архивных копий с живыми скиллами.

У Юрия 3 машины (ПК1, ПК2, ноутбук). Цель: находки и новые скиллы с любой машины
доступны на остальных. Общий хаб скиллов — **приватный** репозиторий
`Yuri-Sverdlov/HERMES-AGENT-SKILL-ARCHIVE`, клон на **всех** ПК по одному пути
`E:\_MY-PROGRAMMING\HERMES-AGENT-SKILL-ARCHIVE` (скиллы — в `skills/<категория>/<имя>/`).
Правила синхронизации описаны в его `SYNC-LOGIC.md` —
прочитай его перед любыми изменениями. Старый хаб `Yuri-Sverdlov/HERMES-AGENT`
(архитектор↔кодер, guides/) содержит устаревшие копии `SOURCES-ARCHIVE*` — не
источник правды.

## Целевая схема (не копии, а подключённый git-клон)

Копии-зеркала устаревают за недели (все найденные копии архива оказались старее
живых скиллов). Поэтому клон репо подключается к Hermes напрямую в `config.yaml`
каждого ПК:

```yaml
skills:
  create_dir: E:/_MY-PROGRAMMING/HERMES-AGENT-SKILL-ARCHIVE/skills   # читается И сюда же пишутся новые скиллы
```

`create_dir` сам по себе сканируется как полноценная папка скиллов — дублировать
её в `external_dirs` не нужно (`external_dirs` оставь для чужих репо вроде
`HERMES-ALL-IN-ONE`). Curator работает только с локальной папкой профиля, так что
скиллы из репо он не архивирует.

`skill_manage patch` правит скилл там, где он лежит → правки тоже идут в репо.
Синк = `git pull` в начале, `git add -A && git commit && git push` в конце.
Справка: `website/docs/user-guide/features/skills.md` (external_dirs, create_dir).
Рабочий образец: `home-accounting` из `HERMES-ALL-IN-ONE` через `external_dirs`.

## Где держать скилл (смешанная схема — предложена, Юрий ещё решает)

Пока решения нет, ничего не переноси между репо: проектные скиллы остаются в
репо проекта, универсальные — в архиве. Спроси, прежде чем менять схему.

| Скилл | Где лежит | Как подключён |
|---|---|---|
| Универсальный (видео, почта, OCR, idea-*, plan…) | `HERMES-AGENT-SKILL-ARCHIVE` | `create_dir` |
| Привязан к коду проекта (`home-accounting`, скилл immergo) | репо самого проекта, внутри git | `external_dirs` |

Почему не всё в архив: скилл проекта вызывает свои скрипты относительно своей
папки; вынесенный отдельно он требует абсолютных путей (разных на ПК/VPS),
двух коммитов на одно изменение (рассинхрон команд), ломает приёмку TASK одним
коммитом и заставляет VPS тянуть все личные скиллы. Проектный скилл вне git
запрещён — теряется при переезде папки. Список проектных скиллов и их
`external_dirs` — в README архива.

Машины-роли: боевой учёт расходов — только VPS (Telegram-бот); ПК — разработка.
Для скилла, чей прод живёт на VPS, на dev-ПК направь данные в явно названную
тестовую базу через переменную окружения, которую читает сам код
(`home-accounting`: `HERMES_FINANCE_DB` → `~/hermes-data/finance-DEV-<ПК>.db`;
`setx` + имя в `terminal.env_passthrough`), а не правкой кода скилла. Hermes видит
переменную только после полного перезапуска приложения — скажи об этом.
Не воспринимай «запиши расход» на ПК как боевую запись без предупреждения.

## Процедура

1. **Аудит.** `git status`, `git fetch`, ahead/behind в каждом хабе; `gh repo list
   Yuri-Sverdlov` — ищи ВСЕ репо со словами HERMES/SKILL (легко пропустить
   отдельный архив-репо и предложить построить его заново). Читай их README /
   SYNC-LOGIC: `gh api repos/<owner>/<repo>/contents/<file> --jq .content | base64 -d`.
2. **Сравни копии по хешам, не по датам** — `python scripts/audit_skills.py <copy1> <copy2> ...`
   (копии ↔ живой `%LOCALAPPDATA%\hermes\skills`; для разошедшихся печатает mtime
   и число строк, чтобы понять, где свежее).
3. **Отфильтруй встроенные скиллы.** Синкаются только личные: исключи то, что
   есть в `hermes-agent/skills`, `optional-skills` и `.bundled_manifest`. Скиллы в
   `.archive/` выключены curator'ом — переносить ли их, спроси.
4. **Приватность до пуша.** Проверь видимость (`gh repo view --json visibility`)
   и дерево на личные файлы (чаты WhatsApp, zip, docx, `app.py`, номера
   телефонов) и ключи. `.gitignore` должен действовать на весь репо, а не на одну
   подпапку. Перевод репо в приватный не чистит историю — скажи об этом.
5. **Сведение версий** в клоне: свежая живая версия перезаписывает архивную;
   переименованные/слитые скиллы (напр. старые загрузчики → `video-fetch`,
   `video-batch-runner`, `video-source-resolve`) сопоставляй по смыслу и
   вливай находки в новое имя, старую папку удаляй. Категории — как в Hermes
   (`media/<skill>/`).
6. **Переключение ПК:** бэкап локальных скиллов → правка `config.yaml` →
   **удалить локальные дубли** перенесённых скиллов → `hermes skills list` /
   `skills_list` показывает их из репо.
7. **Онбординг другого ПК:** сначала его уникальные скиллы/правки коммитятся и
   мерджатся в репо, только потом подключение и удаление локальных копий —
   иначе его находки затрутся.
8. **Проекты, на которые ссылается `config.yaml`** (`external_dirs`,
   `terminal.cwd`): проверь каждый путь; мёртвый — клон проекта на новое место,
   правка пути, оживление проекта. Рецепт — `references/project-revive-on-pc.md`.
9. **Скиллы, созданные в рабочих чатах**, доводи до переносимости: найди их
   (`session_search` по названию чата + untracked в `git status`), перенеси рабочие
   скрипты из рабочей папки ПК в `scripts/` скилла без жёстких путей и докажи
   неизменность поведения на эталонных входах. Рецепт —
   `references/portable-skill-scripts.md`. Скилл, чей скрипт лежит вне его папки, на
   другом ПК неисполним — считай его недоперенесённым.

## Документы репо скиллов (читай перед работой)

| Файл | Для кого | Правило |
|---|---|---|
| `ИНСТРУКЦИЯ-СИНХРОНИЗАЦИЯ-СКИЛЛОВ.md` | начинающий человек | только текущее состояние; меняешь схему — правь и её |
| `ОТЛОЖЕННЫЕ-ВОПРОСЫ-СИНХРОНИЗАЦИИ.md` | Юрий и агент | перед решением по синку проверь, нет ли там пункта; закрыл — удали пункт, решение в `CHANGELOG.md`; новый отложенный вопрос — допиши туда |
| `README.md` / `SYNC-LOGIC.md` / `CHANGELOG.md` | сопровождающий | таблица скиллов в README обновляй при каждом новом скилле |

Порядок при связке «навести порядок со скиллами» + «написать документ»: сначала
скиллы (то, что существует в одном экземпляре, можно потерять), потом документ — он
описывает уже готовое состояние. Как писать сами документы — `project-knowledge-guides`.

## Грабли

- Precedence: `project → local skills/ → create_dir → external_dirs`. Если имя
  есть и локально, и в репо — локальная копия молча затеняет репо, и правки
  уходят не туда. Всегда удаляй локальный дубль после переноса.
- Не предлагай свой export/import-скрипт и хеш-манифест — `create_dir` +
  `external_dirs` + git делают это без копирования; история git показывает,
  что новее.
- Таймстампы врут после облачного/robocopy-копирования — сравнивай хеши.
- Жёсткие пути `C:/Users/Yuri/AppData/Local/hermes/skills/...` в SKILL.md ломаются
  после переезда в репо — заменяй на шаблонную переменную папки скилла
  (HERMES_SKILL_DIR в форме «доллар + фигурные скобки») + `/scripts/...`; для соседнего
  скилла — та же переменная + `/../<скилл>/scripts/...`. При `template_vars: true`
  `skill_view` показывает её уже раскрытой — в прозе правил не пиши её буквально,
  иначе правило читается как «пиши абсолютный путь».
- `external_dirs` с несуществующим путём Hermes молча пропускает — скилл
  просто исчезает. При аудите проверяй каждый путь на диске и что папка —
  git-клон (папки проектов переезжают между `_My_Programming` и
  `_MY-PROGRAMMING_N` и остаются пустыми). Чинится `git clone` в новое место +
  правка пути; проверка — `hermes skills list` показывает скилл с источником
  `external`.
- Потерянные скиллы ищи в `skills/.usage.json`: имена с `use_count`, которых нет
  ни в одной папке скиллов, — были в незакоммиченной папке проекта
  (напр. `.hermes/skills` вне git) и пропали вместе с ней. Скажи об этом и спроси,
  есть ли копия на другом ПК.
- Отличай личные скиллы от встроенных по содержимому: `computer-use-pc2` оказался
  старой копией встроенного `computer-use` (тот же `name:`), а скиллы с датой
  установки Hermes и автором не Юрий — бывшие встроенные. Hub-установки
  (`.hub/lock.json`) не переносим — ставятся командой.
- После правки скилла в репо — сразу `git commit && git push` в
  `E:\_MY-PROGRAMMING\HERMES-AGENT-SKILL-ARCHIVE`, сверка HEAD с `git ls-remote`.
  **Не спрашивай разрешения и не останавливайся на «могу закоммитить, скажи слово»**: запрет
  коммитить без задания из `tasks/TASK.md` — это устав хаба `HERMES-AGENT`, на репо скиллов он
  не распространяется. Там commit+push и есть штатное завершение правки скилла, и Юрий ждёт
  его без напоминаний.
- В дереве могут лежать незакоммиченные правки прошлых сессий. Не откладывай их «на потом»
  и не сваливай в один коммит: сгруппируй по подпапкам в 2–4 осмысленных коммита (свой —
  отдельно) и запушь. В сообщении коммита — что и зачем, без дат и номеров задач.
- Репо — единственный переносчик знания между ПК. Всё, что существует в одном экземпляре на
  одной машине (выгрузка чата, разбор от другого агента на локальном диске), на другие ПК не
  попадёт. Прежде чем отвечать «это другим ПК не нужно», проверь по README / `SYNC-LOGIC.md` /
  `CHANGELOG.md`, что решения из такого файла там уже записаны: если нет — предложи либо
  дистиллировать их в `SYNC-LOGIC.md`, либо положить файл в репо. И наоборот: выгрузка чата
  знания почти не несёт (2/3 содержимого — вывод инструментов) — её место вне git, а не в репо.
  Выгрузку чата Hermes (`*local-ca*.json`) держи вне git отдельной строкой в `.gitignore`,
  но сначала прочитай: она — источник решения, а не мусор.
- Шаги, меняющие `config.yaml` или удаляющие скиллы, — только после бэкапа и
  явного «да» пользователя; аудит и подготовку клона можно делать сразу.
- Юрий может прислать разбор другого агента: сверь его факты со своими
  (хеши), явно перечисли, что тот пропустил и что предлагаешь заменить — с
  обоснованием, а не просто согласие.
- Когда Юрий спрашивает «что это означает / какие проблемы» — объясняй на
  его же скилле/проекте (напр. `home-accounting`), конкретными последствиями, а не
  абстрактно; в конце — рекомендация и один вопрос «приступаю?».
- Ответы — по-русски; итог аудита таблицей «скилл / где свежее / что совпадает»,
  в конце 2–4 конкретных вопроса на решение (обычным текстом, не через clarify).
