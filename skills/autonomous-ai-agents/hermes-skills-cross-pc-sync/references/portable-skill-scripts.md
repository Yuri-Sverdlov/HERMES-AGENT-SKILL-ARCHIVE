# Сделать скилл переносимым: скрипты из рабочей папки — внутрь скилла

Скилл, родившийся в долгой рабочей сессии, обычно описывает метод, а рабочие скрипты
остаются в рабочей папке одного ПК (`%LOCALAPPDATA%\hermes\audio-work\` и т.п.). На другом ПК
такой скилл объясняет, но выполнить его нечем. Рецепт переноса:

## 1. Найти скиллы из чата и их состояние
- `session_search` по названию чата (чаты часто идут серией: «…», «2-…») и по
  `skill_manage create` с `role_filter=user,assistant,tool`.
- В репо: `git status --short --untracked-files=all` — новый скилл часто **untracked**, а правка
  старого — незакоммичена. Скан mtime папок скиллов после даты чата в репо И в локальной
  `%LOCALAPPDATA%\hermes\skills` (имя в обоих — затенение).
- В SKILL.md ищи ссылки на внешние папки (`AppData`, `audio-work`, `C:/Users`) — это маркер
  скриптов, живущих вне скилла.

## 2. Отобрать, что переносить
- Список `*.py` с числом строк, mtime и первой строкой docstring. Рабочие — с docstring и
  суффиксом версии (`*2.py` новее `*.py`); `probe_*`, `validate*`, `clean_b2/b3` — одноразовые
  эксперименты, не переносить. Два почти одинаковых файла сравни `diff` — часто разница
  только в зашитой книге.
- По одному скрипту на шаг конвейера; проверь, что конвейер замкнут (есть шаг между
  OCR-выходом и переводом и т.п.).
- Данные (книги, шрифты, словари, venv'ы) — не в репо; в SKILL.md написать, что должно
  лежать в рабочей папке и в каком venv запускать каждый скрипт.

## 3. Обобщить (минимальные правки, логику не трогать)
- Жёсткий `WORK = r"C:\Users\..."` →
  `os.environ.get("<SKILL>_WORK_DIR") or os.path.join(os.environ["LOCALAPPDATA"], "hermes", "<work>")`.
- Папка вывода с личным путём → переменная окружения с дефолтом внутри рабочей папки.
- Ключ API: сначала `os.environ["OPENROUTER_API_KEY"]`, затем `.env` Hermes через
  `LOCALAPPDATA` (якорный `re.match`), никогда не жёсткий путь. Убрать личные `HTTP-Referer`.
- Зашитые списки книг/файлов по умолчанию → `sys.argv`; без аргументов — `sys.exit(usage)`,
  чтобы случайный запуск не ушёл в чужие данные и не потратил деньги. Книго-специфичные
  константы (глоссарий, колонтитулы) оставить и пометить «править под книгу».
- Правки делай скриптом с `assert s.count(old) == 1` на каждую замену; для `re.sub` с
  текстом замены, содержащим `\s`, передавай `lambda m: text` (иначе `bad escape`). Файлы,
  прочитанные в текстовом режиме, уже с `\n` — искать `\r\n` бесполезно.
- После записи — grep по скриптам на `C:\Users`, имя пользователя, буквы дисков, `sk-or`.

## 4. Доказать, что поведение не изменилось
- Запускай в venv скилла с очищенным окружением (`env -u PYTHONPATH`) и
  `PYTHONDONTWRITEBYTECODE=1` — тогда `__pycache__` не появится и чистить нечего (рекурсивное
  удаление `__pycache__` через `find -exec rm -rf` агенту запрещено). Синтаксис — через
  `ast.parse`, без `py_compile`.
- Детерминированные шаги — прогон на эталонных входах в временную рабочую папку
  (`<SKILL>_WORK_DIR` → scratch, путь в формате Windows, не `/tmp`) и байтовое сравнение с
  старыми артефактами; измерители — те же числа, что записаны в скилле.
- Платные и долгие шаги (API-перевод, озвучка) заново не гонять: скопировать готовый
  выход в тестовую папку и убедиться, что resume пропускает всё (ключ найден, расход $0) +
  проверить usage без аргументов. В отчёте честно разделить «прогнано» и «только
  запуск».

## 5. SKILL.md и коммиты
- Раздел «Scripts»: таблица «шаг / команда через переменную папки скилла / venv», что
  должно лежать в рабочей папке, эталонный результат прогона. Убрать фразы «скрипты
  лежат в …\audio-work». Неоформленную часть метода пометить «не оформлено скриптом».
- Исправить в тексте числа, которые прогон опроверг (напр. порог «битый слой»), во всех скиллах,
  где они цитируются.
- Один коммит на скилл + отдельный на README/CHANGELOG; README-таблицу скиллов обновить.
