# Кто пишет в скиллы автоматически

Два разных автомата. Их постоянно путают, и от этого зависят выводы вида «автоматика скиллы
не трогает» — неверные наполовину.

## 1. Проход curator'а (уборка по времени)

- Меняет **только статусы**: `active → stale` (14 дней без использования) → `archived`
  (30 дней) → папка переезжает в `~/.hermes/skills/.archive/`.
- Ничего не удаляет. Перед прогоном — tar.gz-снапшот (хранит 5); `purge` — только вручную.
- Управляет скиллами с `created_by: agent`. Скиллы во внешнем каталоге (`skills.create_dir`,
  репо) в его ведении не числятся. При `curator.prune_builtins: true` архивирует и неиспользуемые
  ВСТРОЕННЫЕ скиллы — их исчезновение из перечня это и есть, а не поломка установки.
- Отдельный LLM-проход (`curator.consolidate`, по умолчанию ВЫКЛЮЧЕН) умеет: оставить, пропатчить,
  слить перекрывающиеся скиллы в зонтик, заархивировать с `absorbed_into`, переписать ссылки на скиллы
  в cron-заданиях. Один прогон — 50–100 вызовов модели; переименования печатаются картой «старое → новое».
- Отчёты каждого прогона: `~/.hermes/logs/curator/<timestamp>/REPORT.md` и `run.json`.

## 2. Фоновый форк самообучения (`agent/background_review.py`)

- Работает после хода сессии: переигрывает разговор в форк-агенте и решает «надо ли
  сохранить/поправить скилл или память», затем пишет напрямую в хранилища скиллов и памяти.
- Именно он создаёт новые скиллы из разговора и патчит существующие — **в том числе в репо**
  (для профиля репо и есть папка скиллов).
- Выключатель: `auxiliary.background_review.enabled` (fail-open: при поломке конфига остаётся
  включённым). Туда же: `provider`/`model` — перенаправить ревизию на дешёвую модель,
  `max_input_tokens <= 0` — отключить, `extra_tools` — расширить белый список инструментов.

## Как посмотреть, что было

```
hermes curator ledger          # id, когда, кто (curator/agent/user), действие, скилл
hermes curator rollback <id>   # откатить одну мутацию
hermes curator usage           # все скиллы: провенанс, счётчики, последняя активность
hermes curator status          # прогоны, что управляется, что вне ведения
hermes curator list-archived   # что лежит в архиве
hermes curator restore <имя>   # вернуть скилл из архива
hermes curator backup          # ручной tar.gz-снапшот перед рискованным шагом
```

В репо автоматическая правка видна как незакоммиченный diff — его читают, а не смахивают.
Лежат ли в архиве скиллы, которых нет в репо, проверяется простым сопоставлением имён:
такие существуют в одном экземпляре и на другие ПК не попадут. Что с этим делать — раздел
«Отложенные скиллы живут в репо» в SKILL.md: личные скиллы переносим в `skills/.archive/`, который
синхронизируется через git, но невидим для каталога.

## Pin: что даёт и чего не даёт

| Действие | pin влияет? |
|---|---|
| автопереходы curator (stale / archive) | да, пропускаются |
| LLM-ревизия (консолидация) | да, обходит скилл |
| `skill_manage delete` | да, отказывает |
| патч содержимого | **нет** — по устройству; и агент, и фоновая ревизия могут править |
| скилл во внешнем каталоге (репо) | CLI отказывает: «is bundled or hub-installed — cannot pin» → флаг ставится вручную в `~/.hermes/skills/.usage.json` |
| встроенный / хаб-скилл | запинить нельзя; хаб не мутируется никогда, встроенные — только архивация при `prune_builtins` |

Жёсткая заморозка содержимого: выключить форк (`auxiliary.background_review.enabled: false`)
или поставить файлу SKILL.md атрибут «только чтение».

## Проверка утверждений о Hermes (а не о доках на слово)

- Долгие страницы документации приходят через экстрактор обрезанными (голова + хвост) — бери
  исходник страницы: `https://raw.githubusercontent.com/NousResearch/hermes-agent/main/website/docs/<путь>.md`.
- Перечень скиллов в промпте — снимок на старте сессии. В долгой сессии там ещё видны имена, которых
  уже нет: `skill_view(<имя>)` отвечает «not found». Верить живому вызову, а не строке промпта.
- Список команд и их поведение — `hermes curator --help`; исходники — `~/.hermes/hermes-agent/agent/`,
  `~/.hermes/hermes-agent/tools/`.
